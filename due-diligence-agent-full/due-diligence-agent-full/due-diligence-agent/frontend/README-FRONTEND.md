# Frontend Implementation Notes

This implements the frontend described in `Frontend_Flow.pdf` using Next.js
16 (App Router, already scaffolded), TypeScript, and Tailwind v4. Every
endpoint the frontend calls now has a matching backend implementation —
see `../BACKEND-CHANGES.md` for what was added there and why.

## Running it

```bash
cd frontend
npm install
cp .env.local.example .env.local   # point at your backend, defaults to :8080
npm run dev
```

`NEXT_PUBLIC_API_BASE_URL` in `.env.local` controls where the app calls the
Spring Boot backend. `npm run build` and `npm run lint` both pass cleanly.

## Architecture

- **Route groups**: `app/(protected)/*` wraps every logged-in page in one
  `ProtectedRoute` + `Header` layout, matching the spec's request to reuse
  one protection mechanism everywhere. The Admin Dashboard adds a second,
  nested `ProtectedRoute requiredRole="ADMINISTRATOR"` on top of that same
  component rather than a separate mechanism.
- **`lib/api.ts`**: single fetch client. Every backend call goes through
  `request()`, which attaches the JWT, normalizes errors, and force-logs-out
  on 401.
- **`lib/hooks/useAsync.ts`** + **`components/ui/AsyncSection.tsx`**: every
  independent piece of data (each due-diligence section, comparables,
  value history, timeline, utilities, notifications, audit log, etc.) owns
  its own fetch and its own loading/error/empty UI. This is what makes "one
  section fails, the rest of the page still works" (spec section 2, step 3)
  automatic instead of a special case — it's still useful defensive
  behavior even now that every endpoint exists, since any one of them can
  still fail at runtime (bad data, DB hiccup, etc.).
- **`lib/dd-section-status.ts`**: the seven Property Details sections all
  come from one aggregated call (`GET /api/properties/{id}/due-diligence`),
  which wraps each field in `{ data, status: SUCCESS|FAILED, errorMessage }`.
  This helper maps that shape (plus the overall call's own loading/error
  state) into one status per section.
- **Recently viewed properties**: `lib/hooks/useRecentlyViewed.ts` keeps the
  last 5 in `localStorage`, since the backend doesn't track this (spec 4.2).

## Things worth knowing before you demo it

- **Registration always creates a `BUYER`.** The backend hardcodes this on
  register (see `BACKEND-CHANGES.md`), so to see the Agent / Legal
  Reviewer / Financial Institution / Administrator dashboards, promote a
  user's role directly in the database. The register page's copy calls
  this out.
- **Comparables / market trends / value history need real seed data to
  show anything.** They're derived from other properties in the same
  city/state (with lat/lng and tax history populated) rather than an
  external feed — see `BACKEND-CHANGES.md` section 2. With sparse seed
  data they'll correctly show an empty state rather than an error.
- **Changing your email on the Profile page logs you out.** The backend's
  JWT subject is the email address itself, so this is a real limitation of
  the underlying auth design, not a frontend bug — see `BACKEND-CHANGES.md`
  section 4.
- **Report generation is synchronous today**, not the Requested → In
  Progress → Completed lifecycle the spec describes for polling. The
  Report page still polls every 4s while status is pending, so it'll pick
  up an async version of report generation with zero frontend changes;
  today that loop simply never has anything to do.
- **PDF/Excel downloads are generated by small hand-rolled writers**
  (no PDF/Excel library was reachable in the backend's build sandbox — see
  `BACKEND-CHANGES.md` section 6). They're genuinely valid files, just
  plain in styling (no logos, tables are simple rows). Swap in a real
  library backend-side if you want richer output; the frontend doesn't
  need to change either way, since it just links to the download URL.
- **Zoning "compliance indicator"**: there's no explicit compliance
  boolean in the backend's zoning DTO, so `ZoningSection` infers a
  best-effort indicator from `zoningCode` vs. `landUse`. Replace with a
  real field if the backend adds one.
- **`propertyType` filter values** (`SINGLE_FAMILY`, `CONDO`, etc.) on the
  Property Search page are placeholders — swap them for whatever values
  your seed data actually uses; the filter itself works against any string.
